# Context

> 上下文管理与记忆机制 / Context Engineering。

## 学习目标

读完本篇应能回答：

1. 上下文如何决定 Agent 表现，为什么窗口大不等于效果好（硬溢出 vs 有效退化）  
2. Context Engineering 和 Prompt Engineering 的边界在哪  
3. 工程上如何组装上下文：静态规则、动态信息、Token 预算、按需加载  
4. Compaction、结构化笔记、Sub-agent 如何服务长任务  
5. 如何用「同 Agent 不同上下文」对比评测证明 CE 收益  
6. 工作记忆 / 会话记忆 / 长期记忆如何分层、按需灌回窗口  

## 1. 上下文如何决定 Agent 表现

### 1.1 核心观点

Agent **没有独立脑外记忆**：每一跳推理只能看到本轮组装进窗口的内容。  
所以表现 ≈ `模型能力 × 本轮上下文质量 × 工具/编排`，其中上下文往往是最容易被忽视、也最容易拖垮效果的变量。

对照前端：不是「组件写得对就一定渲染对」，还取决于这次 props / store 里塞了什么。上下文就是 Agent 每一拍的 props。

### 1.2 窗口里通常有什么

```text
上下文窗口
├── 静态规则：系统指令、安全边界、输出契约
├── 工具定义：名称、Schema、说明
├── 动态状态：对话历史、任务进度、工具结果
├── 按需证据：RAG / 检索 / DB / 文件片段
├── 当前用户输入
└── 正在生成的输出（占剩余预算）
```

- 缺关键证据 → 幻觉或拒答；
- 噪声太多 → 忽略重点（含 Lost in the Middle）；
- 预算被历史占满 → 新指令/新证据进不去。

### 1.3 为什么窗口大 ≠ 效果好

| 误区               | 实际情况                                |
| ------------------ | --------------------------------------- |
| 窗口越大越聪明     | 利用率不均；中间信息更易被「淹没」      |
| 能塞就全塞         | 噪声上升，延迟/费用上升，有效信号被稀释 |
| 长历史 = 更好记忆  | 未整理的长历史常是重复、过期、冲突信息  |
| 标称 128K 都能用满 | 还要给输出预留；模板与工具定义也占额度  |

要点：

- **硬限制**：Token 上限、输入/输出分账（部分供应商）——见 §1.4 例题 A  
- **软限制**：有效利用长度往往短于标称窗口——见 §1.4 例题 B/C  
- **成本与延迟**：Prefill 随输入变长，TTFT 变差  
- **质量**：相关、及时、可引用的短上下文，常优于「大而脏」的长上下文；用 §5.1 对比评测验证  

一句话：**要的是高信噪比，不是高占用率。**

### 1.4 硬溢出 vs 有效退化（例题）

组装上下文时要同时防两类失败：**硬性溢出**（超窗口直接失败/截断）和 **有效上下文退化**（未超限但用不好）：

| 例题                                                      | 现象                          | 属于                               | CE 侧改法                                      |
| --------------------------------------------------------- | ----------------------------- | ---------------------------------- | ---------------------------------------------- |
| A. 系统+工具+历史+检索合计 30K，窗口 32K，`max_tokens=4K` | API `context_length_exceeded` | **硬溢出**                         | 先压历史/证据；组装前按「输入+预留输出」算预算 |
| B. 总 Token 仅 12K，但把关键退货条款夹在 20 段背景中间    | 模型忽略条款，给出违规方案    | **有效退化**（Lost in the Middle） | 条款置顶/置尾；先引用再分析；少塞背景          |
| C. 未超限，但塞满重复工具 JSON                            | 答非所问、TTFT 变差           | **有效退化 + 成本**                | 工具结果截断；只留字段；原文外置               |
| D. 历史极长仍「能发」，新 System 规则却进不去             | 行为仍像旧版                  | **预算挤占**                       | 固定高优桶不可裁；先裁历史                     |

自测：遇到失败时先问——是 **放不下**，还是 **放下了但没用上**？两者的 Assembler 动作不同。

## 2. Context Engineering vs Prompt Engineering

### 2.1 一句话区分

- **Prompt Engineering**：这一跳里，**怎么写**指令与格式，让模型更稳地完成「当前子任务」。  
- **Context Engineering**：在多跳 / 长任务里，**选什么、存什么、丢什么、何时加载**，让模型每一步都「看得见该看的」。

### 2.2 对照

| 维度     | Prompt Engineering                       | Context Engineering                            |
| -------- | ---------------------------------------- | ---------------------------------------------- |
| 重心     | 措辞、结构、技巧（RTCF、Few-shot、CoT…） | 信息生命周期：采集 → 筛选 → 压缩 → 注入 → 淘汰 |
| 时间尺度 | 单次或少数次调用                         | 会话、任务、跨会话记忆                         |
| 典型问题 | 输出格式不稳、角色跑偏                   | 历史爆炸、证据缺失、工具结果淹没指令           |
| 主要产物 | Prompt 模板、评测集                      | 组装策略、记忆结构、预算与检索策略             |
| 失败表现 | 单次答错/格式烂                          | 越跑越差、前后矛盾、成本失控                   |

### 2.3 关系（不要对立）

```text
Context Engineering 决定「模型看见什么」
Prompt Engineering 决定「在看见的内容上怎么被要求行动」
二者交汇在：每一跳最终发出的那份 messages / tools 载荷
```

![单次PE vs 多跳CE](/assets/pe-vs-ce.png)

读图要点：

1. **每一跳内部**仍然要写 Prompt（PE）——格式、禁止项、工具怎么用。  
2. **跳与跳之间**靠 CE：上一跳的历史/工具结果会不会污染下一跳、预算够不够、要不要检索或压缩。  
3. 交汇点永远是 **Assembler 产出的那份载荷**；PE 写在载荷的「指令层」，CE 决定载荷里还有哪些证据与状态。  
4. 单次问答可以几乎只有 PE；Agent 一多跳，没有 CE 就会「Prompt 写得再好也越跑越脏」。

## 3. 工程上怎么组装上下文

目标：在 Token 预算内，最大化 **任务相关信息密度**，并保证指令与不可信数据边界清晰。

### 3.1 静态规则（Static）

几乎每跳都带、变更低频：

- 角色与安全边界  
- 输出 Schema / 工具使用规范  
- 业务红线（禁止项、拒答策略）  

做法：模板化、版本化（`prompt_version`）、与代码一起发版；控制长度，避免把百科全书写进 System。  
静态段还应尽量**字节级稳定**，以便打上 Prompt Cache。

### 3.2 动态信息（Dynamic）

随任务变化：

- 用户当前输入  
- 最近 N 轮对话或「已确认事实」  
- 工具调用与返回  
- 任务状态机字段（当前步骤、待办、已完成）  

做法：结构化存储（JSON/字段），注入时只取必要字段，而不是整段日志原文。

### 3.3 Token 预算（Budget）

```text
可用输入预算 ≈ 窗口上限 - 预留输出 - 工具定义 - 静态规则 - 安全余量
```

分配示意（比例需按业务调，非标准）：

| 桶       | 作用            | 策略方向             |
| -------- | --------------- | -------------------- |
| 静态规则 | 行为底线        | 短、稳、版本化       |
| 当前任务 | 用户问题 + 状态 | 优先保证             |
| 证据     | RAG/工具结果    | 按相关度截断         |
| 历史     | 连贯性          | 超限则压缩或丢弃最旧 |

**组装前先 count / 估算（Go + 前端落地要点）**

1. **以服务端为准**  
   最终裁剪与是否超限应在 **Go Assembler**（或网关）完成；浏览器侧估算只用于 UX（进度、提示「上下文过长」），不能当作硬配额。

2. **优先用「目标模型」的分词器**  
   不同模型 Token 数不一致。有官方/开源 tokenizer 就用（或供应商 count API）；没有时再退化为估算，并留安全余量（例如按估算值再预留 5%～15%）。

3. **粗估公式（仅兜底）**  
   - 英文为主：`chars / 4` 量级  
   - 中文为主：`chars / 1.5～2` 量级  
   工具 Schema、消息角色包装也会占 Token，估算时应对「整段将发送的文本」计，而不是只计用户可见正文。

4. **按桶计数，再按优先级裁**  
   ```text
   先固定：静态规则 + 工具定义 + 当前任务 + 预留输出
   剩余预算 = 窗口上限 - 上述占用 - 安全余量
   再填：证据 → 历史（超限先压历史，再裁证据）
   ```
   实现上给每段打 `token_estimate` / `token_exact`，裁剪时可单段替换为摘要，避免整包重算前盲目拼接。

5. **Go 侧建议**  
   - Assembler 输入输出带 `Usage{ prompt, reserved_out, by_bucket }`  
   - 超限返回明确错误码（如 `context_budget_exceeded`），由上层决定压缩/拒答/换模型  
   - 对静态前缀做一次精确计数并缓存；动态段每次重算  
   - 日志打 `prompt_tokens`（若响应有 usage）与本地估算的偏差，便于校准系数  

6. **前端侧建议**  
   - 输入框/附件用防抖粗估，超软阈值提示，超硬阈值禁止发送或改为「仅摘要模式」  
   - 流式回复展示时不要用前端估算当计费；账单与限流看服务端 usage  
   - 多模态（图/文件）按供应商规则另计，缺文档时宁可高估  

7. **和 Prompt Cache 的关系**  
   计数对象是「整请求」；稳定前缀可单独统计并缓存其 token 数，但**不要**为了省事把动态内容拼进已缓存前缀再重新计数导致失配。

**Go 伪代码（Assembler 预算）**

```go
// 示意：真实项目应注入 Tokenizer / 供应商 count API
type Bucket string

const (
  BucketStatic  Bucket = "static"
  BucketTools   Bucket = "tools"
  BucketTask    Bucket = "task"
  BucketEvidence Bucket = "evidence"
  BucketHistory Bucket = "history"
)

type Segment struct {
  Bucket Bucket
  Text   string
  Tokens int // 精确或估算
}

func FitBudget(window, reservedOut, safety int, segs []Segment) ([]Segment, error) {
  inputBudget := window - reservedOut - safety
  if inputBudget <= 0 {
    return nil, errBadBudget
  }

  var fixed, flexible []Segment
  for _, s := range segs {
    switch s.Bucket {
    case BucketStatic, BucketTools, BucketTask:
      fixed = append(fixed, s)
    default:
      flexible = append(flexible, s)
    }
  }

  used := sumTokens(fixed)
  if used > inputBudget {
    return nil, errContextBudgetExceeded // 固定桶过大：改模板/换模型，勿盲裁安全规则
  }
  remain := inputBudget - used

  // 灵活桶：先证据后历史；超限时先压 history，再截断 evidence
  sortFlexible(flexible) // evidence 优先于 history 保留（可按业务反过来）
  out := append([]Segment{}, fixed...)
  for _, s := range flexible {
    if s.Tokens <= remain {
      out = append(out, s)
      remain -= s.Tokens
      continue
    }
    trimmed := truncateOrSummarize(s, remain) // 单段处理，保留引用/关键字段
    if trimmed.Tokens == 0 {
      continue
    }
    out = append(out, trimmed)
    remain -= trimmed.Tokens
  }
  return out, nil
}
```

要点：固定桶超限要报错而不是偷偷删 System；灵活桶用「截断/摘要」消化剩余空间；每次裁剪写审计日志（谁被裁、裁前裁后 Token）。

### 3.4 按需加载（Just-in-time）

不把知识库/全仓代码塞进窗口，而是：

1. 先判断缺什么信息  
2. 检索 / 读文件 / 调 API  
3. 只把命中片段写入本跳上下文  
4. 用完可丢，需要时再取  

### 3.5 面向 Prompt Cache 的组装

**Assembler 怎么提高命中率**：

```text
[稳定前缀 · 宜缓存]
  System / 安全边界 / 输出契约
  工具定义 Schema（本阶段固定的那一份）
  少量固定 Few-shot（若长期不变）
[易变后缀 · 不要塞进前缀]
  当前用户输入
  本跳 RAG / 工具结果
  时间戳、请求 ID、用户画像临时字段
```

实践要点：

1. **少变在前、常变在后**；不要在 System 里拼 `now()`、随机数、每请求不同的追踪 ID。  
2. 工具列表按**阶段**装卸可以，但同一阶段内保持顺序与文案稳定；频繁改 description 会导致前缀失配。  
3. 命中失败时先 Diff 前缀：多一个空格、字段顺序变化、JSON 序列化不稳定，都可能整段不命中。  
4. Cache **不提升答案正确性**，只降重复 Prefill 的延迟/费用；信噪比仍靠检索与裁剪。  
5. 具体最小长度、TTL、显式 cache 参数以供应商文档为准，上线用「缓存读写 Token」指标验收。

### 3.6 最小组装流水线（草稿）

```text
1. 放入静态规则与工具定义（稳定前缀，利于 Prompt Cache）
2. 放入任务状态与当前用户输入
3. 按预算决定：历史原文 / 摘要 / 结构化笔记
4. 若缺证据 → 先工具/检索，再进入生成跳（证据放后缀）
5. 生成后：校验 → 更新状态/记忆 → 下一跳重复
```

## 4. 长任务：Compaction、结构化笔记、Sub-agent

长任务（多步改代码、长调研、多工具循环）会迅速撑爆窗口。三类常用手段：

### 4.1 Compaction（压缩 / 折叠）

把过长历史变成更短的等价信息：

- 滑动窗口：只留最近 K 轮  
- 摘要压缩：旧轮次变成「迄今结论」  
- 工具结果截断：只留结论与关键字段，去掉大段原始 payload  

代价：摘要可能丢细节或引入错误 → 关键事实应进「结构化笔记」，不要只靠散文摘要。

**何时摘要 / 何时必须保留原文**

| 内容类型                                | 优先策略                         | 说明                               |
| --------------------------------------- | -------------------------------- | ---------------------------------- |
| 寒暄、重复确认、已过时的中间推理        | **摘要或丢弃**                   | 对后续决策几乎无增量信息           |
| 早期多轮闲聊式历史                      | **摘要**                         | 压成「用户目标 / 已确认偏好」即可  |
| 冗长工具日志、HTML、全量 API JSON       | **截断 + 摘要**                  | 窗口内只留结论字段；原文外置存储   |
| 已消化完的旧 `tool_result`              | **清理原文，可留调用记录**       | 保留「调过什么」；payload 不必常驻 |
| 当前子任务正用到的证据段落              | **保留原文（或高相关片段）**     | 正在引用的内容不要先摘要再问       |
| 安全/合规红线、权限边界、硬约束         | **必须原文**                     | 摘要易软化或写丢禁止项             |
| 金额、日期、ID、版本号、错误码、traceId | **必须原文（或结构化字段）**     | 禁止只靠「大概是超时」类概括       |
| 用户明确拍板的决策与验收标准            | **原文或写入笔记字段**           | 「已同意方案 B」不可被摘要成含糊句 |
| 排障所需的异常栈 / 关键日志片           | **原文短摘 + 回查链接**          | 可裁长度，但不能只剩「报错了」     |
| 合同/法规/政策被引用的句子              | **原文引用 + doc_id**            | 先引用再分析；摘要不能代替条款     |
| 多跳后仍反复用到的稳定结论              | **进结构化笔记，窗口内引用笔记** | 比反复摘要聊天记录更稳             |

经验口诀：

- **要算、要对、要追责 → 留原文或结构化字段**  
- **只为连贯、已用完、可回查 → 摘要 / 外置 / 丢弃**  
- 不确定时：先把关键字段写入笔记，再对散文历史做摘要，避免「唯一真相」活在摘要里。

**Compaction 策略与失败案例**

| 策略                | 做法                          | 适用             | 典型失败                      |
| ------------------- | ----------------------------- | ---------------- | ----------------------------- |
| 滑动窗口            | 只留最近 K 轮原文             | 短对话、局部连贯 | K 太小丢掉仍有效的约束        |
| 分段摘要            | 旧轮次 →「迄今结论」段落      | 长会话           | 摘要写丢数字/决策；幻觉进摘要 |
| 工具结果清理        | 留 tool_use，清旧 tool_result | 多工具 Agent     | 清太早，后续步还要原始字段    |
| 笔记外置 + 窗口引用 | 真相进笔记，窗口只挂摘要指针  | 长任务           | 笔记未更新，窗口与笔记不一致  |

失败案例（简）：

1. **摘要漂移**：把「7 天无理由，已过期」压成「仍可退」→ 后续错误履约。  
   防：金额/日期/状态进笔记字段，摘要禁止改写这些字段。  
2. **清结果过早**：第二步还要 `traceId`，第一步已删日志 → 排障断线。  
   防：按「引用计数 / 过期步数」清理，不按「已读过」一刀切。  
3. **只压不记**：每轮摘要覆盖上轮，关键决策蒸发。  
   防：Compaction 与结构化笔记双写；笔记是真相源。

### 4.2 结构化笔记（Structured Notes / Scratchpad）

在窗口外（或窗口内固定槽位）维护机器可读状态。每跳只注入笔记 + 当前子任务，而不是全文聊天记录。

**字段规范示例（JSON）**

```json
{
  "schema_version": "1.0",
  "task_id": "return-20260325-001",
  "goal": "为用户办理耳机换货并确认库存与时效",
  "constraints": [
    "仅使用工具返回的订单与库存数据",
    "不编造物流单号"
  ],
  "decisions": [
    {
      "at": "2026-03-25T10:02:00Z",
      "by": "user|agent|human",
      "text": "用户同意换货，不退款",
      "evidence_refs": ["tool:get_order#1"]
    }
  ],
  "facts": {
    "order_id": "O123",
    "sku": "WH-1000XM5",
    "within_return_window": true,
    "warranty_until": "2027-03-25"
  },
  "open_questions": ["仓库是否有同色库存"],
  "artifacts": [
    {
      "id": "inv-1",
      "type": "tool_result_ref",
      "path_or_uri": "s3://.../check_inventory.json",
      "summary": "同款黑色有货，ETA 2-3 天"
    }
  ],
  "next_actions": ["call check_inventory", "confirm with user"],
  "updated_at": "2026-03-25T10:05:00Z"
}
```

更新时机：工具成功返回后写 `facts`/`artifacts`；用户确认后写 `decisions`；Compaction 前把易丢字段刷进笔记。  
窗口注入时通常只带：`goal + constraints + facts + open_questions + next_actions`（按预算再裁）。

### 4.3 Sub-agent（子代理 / 子上下文）

把子任务丢给「干净窗口」的子调用：父持目标与笔记并编排；子只带最小上下文，返回结构化结果；父写入笔记并丢弃子过程噪声。

**输入 / 输出契约模板**

```text
# Sub-agent Input
{
  "parent_task_id": "...",
  "subgoal": "只核查该订单是否在退换期内，并给出截止日期",
  "allowed_tools": ["get_order"],
  "facts_subset": { "order_id": "O123" },          // 最小事实，勿塞全历史
  "constraints": ["不得下单", "不得改地址"],
  "output_schema": "ReturnWindowResult"
}

# Sub-agent Output（必须可校验）
{
  "status": "ok | failed | need_clarification",
  "result": {
    "within_window": true,
    "deadline": "2026-04-01",
    "evidence_refs": ["tool:get_order#1"]
  },
  "tokens_used": 1800,
  "notes_for_parent": "保修与退换政策以订单快照为准"
}
```

契约要点：工具白名单、禁止副作用、输出 Schema、证据引用；父 Agent **禁止**把子 Agent 的思维链全文拼进主窗口。

### 4.4 怎么选（简表）

| 手段       | 更适合                 | 注意                 |
| ---------- | ---------------------- | -------------------- |
| Compaction | 历史重复多、细节可变糊 | 防摘要漂移           |
| 结构化笔记 | 长任务、要跨跳一致     | 要设计字段与更新时机 |
| Sub-agent  | 子任务可边界化、工具脏 | 要定义返回契约与权限 |

可组合：笔记做真相源 + 局部 compaction + 重活交给 sub-agent。

## 5. 同样的 Agent，为什么表现差这么多？

表面「同一个 Agent」（同一模型、同一套提示），常见真正变量在上下文与组装：

| 原因                | 表现                       | 排查方向                        |
| ------------------- | -------------------------- | ------------------------------- |
| 证据有无 / 是否过期 | 一个靠谱一个胡说           | 本跳是否注入了正确检索/工具结果 |
| 历史污染            | 越聊越乱、指令被旧对话带偏 | 历史策略、是否该 compaction     |
| 预算挤占            | 新规则/新证据进不去        | Token 分配与截断顺序            |
| Lost in the Middle  | 「明明塞了却没用」         | 关键约束位置、材料组织          |
| 工具结果过长        | 模型盯着日志忽略任务       | 结果裁剪与结构化                |
| 模板版本不一致      | 线上线下两套行为           | `prompt_version` / 配置         |
| 不可信内容未隔离    | 被邮件/文档注入带跑        | 认知层分区                      |
| 评测样本不同        | 「感觉变差」               | 固定集回归，而不是个例体感      |

一句话：**模型往往没换，换的是每一跳「看见的世界」。** 调表现优先查上下文组装与记忆，而不是先怪模型或先改一大段文案。

### 5.1 「同 Agent 不同上下文」对比评测设计

目的：证明差距来自 **Assembler**，而不是模型或文案玄学。

**固定变量：** 模型、Temperature、System Prompt 版本、工具实现、同一批用户话术。  
**变化变量：** 仅上下文策略（无检索 / 有检索 / 脏历史 / 压缩后 等）。

| 用例 ID | 用户话术               | 上下文条件 A（弱）     | 上下文条件 B（强）       | 成功标准                     |
| ------- | ---------------------- | ---------------------- | ------------------------ | ---------------------------- |
| C01     | 上周耳机坏了怎么处理   | 无订单工具结果         | 注入订单+保修期+库存工具 | 给出可执行方案且关键字段正确 |
| C02     | 按政策能否第 10 天退货 | 长文档、条款在中间     | 条款置顶 + 要求引用      | 结论正确且带 quote/doc_id    |
| C03     | 继续刚才的换货         | 未压缩的 30 轮噪声历史 | 笔记 facts + 最近 4 轮   | 不追问已确认信息、不矛盾     |
| C04     | 根据日志说根因         | 全量 50KB 日志         | 摘要+traceId+关键栈短摘  | 指出错误码且可回查           |

执行：每条件跑 N 次（如 3～5），记成功率、字段正确率、平均 prompt_tokens、TTFT。  
每次只改一个 CE 旋钮；结论写入评测报告，避免「感觉 B 更好」。

## 6. 记忆分层：工作记忆 / 会话记忆 / 长期记忆

上下文窗口是 **工作记忆**；外面还应有分层存储，按需再灌回窗口。

| 层级         | 是什么                 | 典型载体                 | 写入                   | 读入窗口                   |
| ------------ | ---------------------- | ------------------------ | ---------------------- | -------------------------- |
| **工作记忆** | 本跳 Assembled 载荷    | messages / tools         | 每跳重建               | 全部（受预算裁剪）         |
| **会话记忆** | 本 Session 状态与笔记  | Redis / DB / `NOTES`     | 工具后、决策后、压缩前 | 摘要或结构化子集           |
| **长期记忆** | 跨会话偏好、档案、知识 | 画像表 / 向量库 / 文件库 | 显式确认或周期性沉淀   | RAG/按需检索，带时间与来源 |

原则：

- 长期记忆 **不能**当工作记忆用：必须检索/过滤后再进窗口。  
- 写入要带 `source / time / confidence`，读取时防记忆污染（过期偏好当现状）。  
- 会话笔记（§4.2）是会话记忆的主干；长期层只沉淀稳定、可复用、低敏感或已脱敏内容。

```text
长期记忆 --检索--> 会话笔记/状态 --组装--> 工作记忆(窗口) --> LLM
                ↑                        |
                └──── Compaction / 工具结果写回 ─┘
```

本篇先建立分层即可：避免「全塞窗口」或「全指望向量库」；向量库细节、遗忘策略等属于长期记忆实现，不在此展开。

## 7. 核心认识

1. Agent 的「记忆」首先是**你组装进窗口的东西**，不是模型自动记住。  
2. 窗口是容量上限，不是质量保证；先分清放不下还是没用上。  
3. PE 管怎么说，CE 管看见什么、留下什么；长任务必须做 CE。  
4. 静态规则要短而稳（兼利 Prompt Cache），动态信息要结构化，证据要按需加载，全程要有 Token 预算。  
5. 长任务靠压缩、笔记、子上下文隔离；摘要不能代替可追责字段。  
6. 用固定话术 + 只改上下文的对比评测，证明 CE 收益。  
7. 工作 / 会话 / 长期记忆分层，按需灌回窗口，避免污染与爆炸。  
8. 表现波动时，先审计本跳上下文，再改提示词或换模型。
