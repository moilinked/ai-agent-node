# Agent 架构与工作流程

> 把「能聊天的模型」做成「能稳定做事的系统」：核心范式、编排形态、工作流程（Agent Loop）、工具接入、状态与失败路径。

## 学习目标

读完本篇应能回答：

1. Agent、传统编程、Workflow 各自解决什么问题，如何组合而不是对立  
2. 生产 Agent 要分层看哪些问题，哪些层最容易被 Demo 低估  
3. 为什么推荐「确定性 Workflow 做骨架，Agent 只在判断点决策」  
4. ReAct、Plan-and-Execute、Reflection、Multi-Agent、Agentic Workflow 各自解决什么；A2A 为何是互通层而非推理范式  
5. 常见编排形态各自适合什么、失败时会怎样  
6. Function Calling、Skill、MCP/Registry 各在哪一层，怎么选型而不混为一谈  
7. 一条 Agent Loop 里，目标、规划、工具、循环、人工、完成判定分别怎么钉死  
8. 生产优先级为何是 Workflow / State / Tool / Observability / Eval  

---

## 1. Agent、传统编程与 Workflow

三者不是互斥流派，而是**决策权放在哪里**不同。搞混了，会要么用 Agent 硬扛本该写死的业务规则，要么用传统 if/else 硬编码本该留给模型的开放判断。

### 1.1 一句话区分

|                  | 传统编程                      | Workflow（工作流 / 状态机） | Agent                           |
| ---------------- | ----------------------------- | --------------------------- | ------------------------------- |
| **下一步由谁定** | 开发者写死的分支与函数调用    | 预定义图：节点与边上的条件  | 模型根据目标与观察动态选择      |
| **不确定性**     | 尽量消除（确定输入→确定输出） | 路径大体确定，允许条件分支  | 主动拥抱：缺信息就查工具/再规划 |
| **典型形态**     | API / 服务 / 脚本             | BPM、审批流、Graph、状态机  | ReAct 循环、工具调用、多跳推理  |
| **可预期性**     | 最高                          | 高（路径可枚举）            | 较低（同输入也可能不同路径）    |
| **擅长**         | 精确计算、事务、权限、计费    | 多步骤业务、审计、恢复      | 理解自然语言、选工具、填洞      |

### 1.2 三种「控制流」长什么样

**传统编程：**

```text
if (withinReturnWindow) {
  createRefund()
} else {
  reject()
}
```

规则、边界、错误码全在代码里；换政策要改代码发版。

**Workflow：**

```text
Start → 查订单 → [可退?] → 是 → 创建退款 → End
                      └→ 否 → 说明原因 → End
```

「走到哪」由图与 Condition 决定；节点内可以是普通代码，也可以挂一个 Agent。路径可画、可测、可回放。

**Agent（狭义的自主循环）：**

```text
Goal → Think → Tool? → Observe → Think → … → 自认完成
```

「下一步调什么」由模型当场决定，不预先画全部分支。灵活，但若不加护栏，路径不可枚举、难恢复。

### 1.3 对照前端心智

| 概念     | 前端近似                                                       |
| -------- | -------------------------------------------------------------- |
| 传统编程 | 工具函数、`useReducer` 里写死的 transition                     |
| Workflow | 路由表 + 多步向导：`step` 与合法跳转预先定义                   |
| Agent    | 用户随便点、组件自己猜下一步（没有路由表）——能力强但必须加护栏 |

生产 Agent 更像：**向导骨架（Workflow）+ 某几步里嵌入智能助手（Agent）+ 提交/扣款仍走传统事务代码**。

### 1.4 怎么选（避免「过度 Agent 化」）

| 问题特征                                         | 更合适                                                |
| ------------------------------------------------ | ----------------------------------------------------- |
| 规则清晰、要强一致、要计费/权限精确              | **传统编程**                                          |
| 多步骤、要审计/断点续跑，但分支可预先画出        | **Workflow**                                          |
| 输入是自然语言、路径事先画不全、需要选工具补信息 | **Agent**（节点内）                                   |
| 上面三者都有                                     | **Workflow 骨架 + 关键节点 Agent + 副作用用传统代码** |

常见误区：

1. **凡事先 Agent：** 退货窗口这种硬规则也丢给模型 → 幻觉履约、难追责。  
2. **凡事先传统代码：** 开放客服意图、非结构化诉求全写 if/else → 组合爆炸、改不动。  
3. **把 Workflow 和 Agent 对立：** Workflow 管路径，Agent 管节点内判断；Graph 正是二者的组合。

一句话收束：

> **传统编程保证正确性，Workflow 保证可控路径，Agent 处理开放决策。**  
> 生产默认不是「纯 Agent」，而是三者各司其职。

## 2. 架构关注点（分层）

| 层次     | 关注点                              | 核心问题                               |
| -------- | ----------------------------------- | -------------------------------------- |
| 模型层   | LLM / 多模型                        | 用什么模型？要不要拆小模型/推理模型？  |
| 认知层   | Planning / Reasoning / Reflection   | 一步做完，还是规划→执行→检查→修正？    |
| 工具层   | API、搜索、代码、DB、浏览器         | 能做什么？失败、超时、重试怎么走？     |
| 知识层   | RAG、知识库、证据注入               | 企业知识与外部事实从哪来、如何进窗口？ |
| 记忆层   | 短期 / 会话 / 长期                  | 记什么、记多久、何时召回？             |
| 状态层   | Session / Task State                | 长任务做到哪一步？如何恢复？           |
| 编排层   | Router / Orchestrator / Multi-Agent | 单 Agent 还是多 Agent？如何分发？      |
| 安全层   | 权限、Guardrails、沙箱              | 哪些可自动执行？哪些必须确认？         |
| 可观测层 | Log、Trace、Token、Cost             | 为何如此决策？哪里失败？花了多少？     |
| 评估层   | Eval / Benchmark                    | 有没有把事情做好？回归是否通过？       |

Demo 阶段常盯 Prompt 与模型；生产出问题往往不是「模型不会答」，而是：

- **状态丢失**（断点不可恢复）  
- **工具异常**（超时、半成功、幂等没设计）  
- **权限过大**（能调的不等于该调）  
- **上下文污染**（脏历史/脏工具结果拖垮下一步）  
- **无限循环**（无 max steps / 无终止条件）  
- **不可观测**（无法解释「为什么做了这个 tool call」）  

其中最容易被低估的是：**状态、权限、可观测**。

## 3. 主线：Workflow 做骨架，Agent 做判断

早期常见形态：

```text
LLM → Prompt → Tools（循环）
```

生产上更稳的形态：

```text
Workflow / Graph（确定性骨架）
        │
        ▼
  需要智能判断的节点 ← Agent
        │
        ▼
  Tools / MCP / API
        │
   State + Trace + Eval
```

一句话：

> **Workflow outside, Agent inside.**  
> 确定性流程包住不确定决策；不要让 LLM 在整条链路上「自由游荡」。

对照前端：路由与状态机管页面流转；组件里再写交互逻辑。Agent 编排同理 -- 图/状态机管「走到哪」，节点内再让模型决定「怎么做」。

## 4. Agent 核心范式

「范式」这里指**控制与协作的基本模式**：谁规划、谁执行、谁检查、多个 Agent 如何协作。  
它们不是互斥产品，也不是越新越好；同一系统里常组合使用。Single Agent、Graph、Supervisor 等，多是这些范式的工程落地。

### 4.1 ReAct（Reason + Act）

交替进行推理与行动，用观察更新下一步：

```text
Thought → Action（Tool）→ Observation → Thought → … → Answer
```

|              |                                                       |
| ------------ | ----------------------------------------------------- |
| **解决什么** | 缺信息时边做边想；工具结果驱动下一跳                  |
| **适合**     | 查询、排查、步骤事先画不全的短中任务                  |
| **风险**     | 无 `max_steps` 易空转；Thought 噪声占窗口；易局部最优 |

工程上就是最常见的 **单 Agent + Tools 循环**。简单任务往往够用；复杂业务再叠规划或外层 Workflow。

### 4.2 Plan-and-Execute

先给出（或修订）计划，再按步执行；执行中可重规划：

```text
Plan → Execute step 1 → … → Execute step N →（可选 Replan）→ Done
```

|              |                                                        |
| ------------ | ------------------------------------------------------ |
| **解决什么** | 多步依赖、要先对齐路线再动手                           |
| **适合**     | 调研报告、迁移方案、明确阶段的长任务                   |
| **风险**     | 计划幻觉（步骤不可行）；过度规划抬延迟；计划与执行脱节 |

和 ReAct 对比：ReAct **即时**选动作；Plan-and-Execute **先地图后赶路**。  
落地时：计划应是短结构化步骤（可进 Task State），不要长篇散文；强业务流程更宜把「计划」下沉为 Workflow 节点，而不是每次让模型从头写计划。

### 4.3 Reflection（含 Critic）

生成之后再审视，不通过则修订重来：

```text
Generate → Reflect / Critique → Revise ↺ → Accept
```

|              |                                          |
| ------------ | ---------------------------------------- |
| **解决什么** | 抬质量、抓明显错误与遗漏                 |
| **适合**     | 代码、文案、分析结论等可复查产出         |
| **风险**     | 两模型互夸「假通过」；无轮次上限烧 Token |

Reflection 可以是同一 Agent 的自检，也可以是独立 Critic。  
有效前提：**可检查标准**（测试、Schema、规则、业务状态），而不是只靠「另一个模型感觉好不好」。Loop / Critic 是其结构展开。

### 4.4 Multi-Agent

多个 Agent 分工：按角色、领域或阶段拆开，再汇总或转交。

常见组织方式：

- **Supervisor + Specialists**：主管拆派与汇总  
- **并行 Workers**：可拆子任务同时做再合并  
- **Handoff**：按意图动态转交  

|              |                                                    |
| ------------ | -------------------------------------------------- |
| **解决什么** | 角色专注、并行与专业边界；**分窗口**时可隔离上下文 |
| **适合**     | 多领域、脏工具链、可并行调研                       |
| **风险**     | 协调与 Token 成本；契约不清则无法合并；转交环      |

注意：多 Agent **不会自动**带来上下文隔离——共享同一会话窗口时，脏历史照样互相污染。隔离是编排设计的结果，不是标签效应。

Multi-Agent 是**手段不是目标**：分不清边界时，先把单 Agent + Workflow 做稳。

### 4.5 A2A（Agent-to-Agent）

这里的 **A2A** 主要指 Agent 之间的**互操作协议/协作接口**（业界有公开的 Agent-to-Agent 一类标准）：让不同框架、厂商的 Agent 能发现对方、委派任务、交换结果。具体字段与版本以官方文档为准。

和邻近概念分开：

|                        | 管什么                  | 典型问题                      |
| ---------------------- | ----------------------- | ----------------------------- |
| **MCP**                | Agent ↔ Tool / Resource | 能力怎么标准接入              |
| **A2A**                | Agent ↔ Agent           | 异质 Agent 怎么协作、委派     |
| **进程内 Multi-Agent** | 同一 Runtime 里多角色   | 代码里直接调另一个 Agent 函数 |

要点：

- A2A **不是**又一种推理范式，而是**协作与互通的层**；里面的每个 Agent 仍可用 ReAct / Plan-and-Execute 等。  
- 与 MCP **互补**：MCP 装备单个 Agent 的工具，A2A 让多个独立 Agent 协作。  
- 生产仍要自建：鉴权、租户、审计、任务状态与超时；协议不会自动给你治理。  
- 单产品内部几个 Specialist，进程内编排通常更简单；跨团队/跨厂商/跨运行时复用时，A2A 这类标准才更有价值。

### 4.6 Agentic Workflows

**Agentic Workflow** = 以 Workflow / Graph 为骨架，在需要智能的节点嵌入 Agent（ReAct、计划、Reflection 等），其余用确定性代码与规则。

```text
确定性节点（校验/写库/通知）
        ↕
  Agentic 节点（理解/选工具/生成）
        ↕
确定性节点（分支/审计/结束）
```

这与 §3「Workflow outside, Agent inside」是同一主线：  
不是让模型自由跑完全程，而是**在可控路径里局部使用范式**。

相对「纯 ReAct 从头逛到尾」：更可测、可恢复、可审计；相对「纯传统工作流」：在开放理解与工具选择处保留模型能力。

### 4.7 范式怎么选（简表）

| 范式             | 更先问                   | 常与谁组合                       |
| ---------------- | ------------------------ | -------------------------------- |
| ReAct            | 信息是否边做边齐？       | 单 Agent；Workflow 内某节点      |
| Plan-and-Execute | 是否必须先对齐多步路线？ | State 中的短计划；复杂则改 Graph |
| Reflection       | 有没有硬验收标准？       | Loop / Critic；测试与规则        |
| Multi-Agent      | 是否真有边界与并行收益？ | Supervisor / Workers / Handoff   |
| A2A              | 是否跨运行时/厂商协作？  | 各 Agent 自带 MCP 工具           |
| Agentic Workflow | 路径能否预先画出大半？   | 上列范式作为节点策略             |

经验：默认 **Agentic Workflow 做外壳**，节点内按需用 ReAct；要质量加 Reflection；要分工再 Multi-Agent；要跨系统互通再考虑 A2A。

## 5. Single Agent + Tools

最基础形态：一个 Agent，一组工具，典型 **ReAct** 循环（§4.1）。

```text
User → Agent ⇄ Tools → Observation → Agent → …
```

```text
Reason → Tool Call → Observe → Reason → … → Final Answer
```

**适合：** 客服查询、搜索、简单 SQL/代码助手、个人助理等边界清晰的任务。

|      |                                  |
| ---- | -------------------------------- |
| 优点 | 简单、MVP 快、链路短             |
| 缺点 | 长任务易跑偏；流程弱；难测难恢复 |

**工程底线：** `max_steps`、工具超时、结果截断、禁止无权限副作用。没有这些，单 Agent 也会在生产上失控。

## 6. Graph / Workflow Agent

把行为组织成状态图：Node（步骤）、Edge（转移）、Condition（分支）、State（共享状态）、Persistence（可恢复）。

一句话：**用确定性流程图钉死「走到哪」，只在少数节点让模型决定「怎么做」。**（即 §3 的 Workflow outside, Agent inside。）

### 6.1 和「单 Agent 乱转」差在哪

单 Agent + Tools 常见是整条链都靠模型自由发挥：

```text
用户一句话 → 模型想下一步 → 调工具 → 再想 → … → 直到自己觉得说完了
```

长任务易跑偏，难回放、难断点续跑。

Graph / Workflow 则是：

```text
图上预先画好路径与分支
  → 每走到一个「Agent 节点」才调用 LLM 做本步判断
  → 其余边、重试、落库由代码/状态机决定，不交给模型
```

对照前端：像带路由的**多步表单向导 / 页面状态机**——`step` 与 store 管流转；不是一个大组件里随便跳。图管「走到哪」，节点内再让模型决定「怎么做」。

### 6.2 图上的基本零件

以「电商退货」为例：

| 概念            | 含义               | 例子                                             |
| --------------- | ------------------ | ------------------------------------------------ |
| **Node**        | 一步工作单元       | `查订单`、`判是否可退`、`创建退款单`、`人工确认` |
| **Edge**        | 走完 A 之后去哪    | `查订单` → `判是否可退`                          |
| **Condition**   | 分支依据           | `within_window == true` → 退款；否则 → 拒绝说明  |
| **State**       | 全图共享的任务数据 | `order_id`、`step`、`facts`、工具结果摘要        |
| **Persistence** | 状态落库           | 进程挂了也能从「已查到订单」接着跑               |

示意：

```text
Start → Router → Research / Coding → Evaluate
                                      /    \
                                   Pass    Fail → Replan → …
```

读作：先路由意图 → 进对应能力节点 → 用规则或检查节点判 Pass/Fail → 失败走重规划边，而不是在无结构对话里无限聊。

### 6.3 核心节奏：确定性 ↔ 智能判断

```text
确定性流程          Agentic Decision         确定性流程
─────────          ─────────────────         ─────────
校验入参、鉴权      「这单能不能退？           写 DB、发通知、
写死下一步边        引用哪条政策？」           记审计日志
```

- **确定性**：规则/代码能做的，不要浪费模型（也更稳）。  
- **Agentic**：需要理解自然语言、综合证据、选工具的，才进 LLM 节点。

节奏就是：

```text
确定性流程 → Agentic Decision → 确定性流程 → Agentic Decision → …
```

### 6.4 适合什么、相对单 Agent 多了什么

**适合：** 复杂业务流程、要审计/回放、要断点续跑的生产任务。

| 能力   | 单 Agent 循环            | Graph / Workflow                     |
| ------ | ------------------------ | ------------------------------------ |
| 可控   | 弱（下一步靠模型）       | 强（边与分支可写死）                 |
| 可测   | 难（路径组合爆炸）       | 可测单节点 + 固定路径                |
| 可恢复 | 常从头重来               | State 持久化后从节点续跑             |
| 审计   | 「模型说了啥」难对齐业务 | 「走过哪些节点、State 怎么变」可追溯 |

|      |                              |
| ---- | ---------------------------- |
| 优点 | 可控、可测、可恢复、易 Debug |
| 注意 | 见下节                       |

选型默认优先考虑这一类：不是因为「更时髦」，而是**失败路径与恢复**写得进系统里。

### 6.5 注意：图上挂了 Agent ≠ 自动变稳

- 节点输入/输出若无契约（Schema），上一步散文会污染下一步。  
- 节点切太碎 → 编排复杂；切太粗 → 又变回「大泥球 Agent」。  
- Evaluate 若只靠「另一个模型感觉好不好」、没有硬标准（规则 / 测试 / 业务状态），Loop 会空转。  

单 Agent Loop 可以看作图里**某一个** Agentic 节点的实现雏形；业务变复杂时，再把多个 Loop / 确定性步骤嵌进同一张 Graph。

## 7. Supervisor + Specialist Agents

一个主管拆任务、分派、汇总；多个专家只做领域子任务。

```text
            Supervisor
                │
     ┌──────────┼──────────┐
     ▼          ▼          ▼
 Research    Coding      Data
     │          │          │
     └──────────┼──────────┘
                ▼
            Supervisor → User
```

Supervisor 职责：理解 → 拆解 → 选 Agent → 分配 → 汇总 → 判断下一步 → 输出。  
Specialist：窄目标、少工具、干净上下文，返回**可校验结构**，而不是把思维链全文交回。

**适合：** 企业 Copilot、多域知识助手、复杂 Coding/数据分析。

**风险：** Supervisor 成为单点瓶颈或「万能提示词」；专家返回散文导致无法合并。  
**防：** 输入/输出 Schema、工具白名单、父级只合并结构化结果。

---

## 8. Orchestrator + Parallel Workers

可高度并行拆分的任务（Deep Research、竞品调研、大库分片分析）：

```text
Lead → Planning → Worker A / B / C → Synthesis → Report
```

**适合：** 子问题近似独立、合并逻辑明确。  
**不适合：** 强串行依赖——硬拆只会抬高 Token、延迟与协调成本。

合并前要定义：冲突怎么解、引用怎么留、失败 worker 是重试还是降级。

---

## 9. Handoff / Swarm

按意图动态转交，而不是固定 Supervisor 树：

```text
User → Triage → Order / Refund / Technical …
```

**适合：** 客服路由、多角色业务线。  

**典型失败：** A→B→C→A 转交环。必须设：

- 最大 handoff 次数  
- Termination / Timeout  
- Cost / Token 上限  
- 全链路 Trace  

Handoff 不是「多个聊天机器人互抛」，而是**带状态与契约的路由**。

---

## 10. 三种基本结构

复杂 Workflow / Graph 多半不是全新发明，而是用 **Sequential / Parallel / Loop** 拼出来的。先认清依赖关系，再选结构；选错会要么拖慢（该并行却串行），要么合并灾难（不该并行却并行），要么烧 Token（无护栏的 Loop）。

Sequential ≈ 多步向导；Parallel ≈ `Promise.all` + 汇总；Loop ≈ `while` + 明确 `break` 条件。

### 10.1 Sequential（串行）

```text
Research → Analyze → Write → Review
```

后一步**必须吃到**前一步的产出，才有资格启动。

|                |                                                                                         |
| -------------- | --------------------------------------------------------------------------------------- |
| **何时用**     | 有明确数据/逻辑依赖：没有调研结论就无法分析；没有分析稿就无法成文                       |
| **优点**       | 路径简单、可预期、易测、易审计（状态按步前进）                                          |
| **代价**       | 总延迟 ≈ 各步之和；前步慢会堵住整条链                                                   |
| **State 要点** | 每步写入结构化结果（摘要/字段），下一步只读契约内字段，不把上一步全文思维链原样塞进窗口 |

失败怎么走：某步失败 → 重试该步 / 回退到上一检查点 / 整单 `failed`，而不是跳过依赖硬跑后面。

**例：** 退货里「查订单 → 判窗口 → 创建退款」必须串行；没有订单快照就不能判窗口。

### 10.2 Parallel（并行）

```text
        ┌→ A ─┐
Input ──┼→ B ─┼→ Merge
        └→ C ─┘
```

子任务彼此**近似独立**（不互相等结果），可同时跑，最后在 Merge 合并。

|                |                                                                          |
| -------------- | ------------------------------------------------------------------------ |
| **何时用**     | 子问题可拆且合并逻辑清晰：市场/技术/竞品三路调研；大库分片扫描           |
| **优点**       | 墙钟时间接近「最慢那一路」，而不是三路相加                               |
| **代价**       | 协调与 Token 成本上升；Merge 要处理冲突与部分失败                        |
| **State 要点** | 各 worker 写到自己的槽位（`result_a/b/c`）；Merge 只读槽位，定义冲突规则 |

Merge 必须事先约定，例如：

- **全成功才继续** vs **允许部分成功并标注缺失**  
- 数字/结论冲突时：以哪路为准，或升级人工  
- 超时 worker：取消、降级占位，还是整单失败  

**不要并行的信号：** B 的输入必须来自 A 的输出；强串行硬拆只会抬延迟与协调成本（见 §8）。

**例：** 「市场规模 / 技术趋势 / 竞争格局」三路可并行；「先定位 bug → 再改代码 → 再跑测试」不能并行。

### 10.3 Loop（循环）

```text
Generate → Review → Improve ↺ → Output
```

同一步骤形态重复，直到**通过标准**或**触及护栏**。

|            |                                                               |
| ---------- | ------------------------------------------------------------- |
| **何时用** | 内容打磨、Code Review、自我修正、质量抬升；一次生成达不到验收 |
| **优点**   | 用多轮换质量，不必指望单次生成完美                            |
| **风险**   | 无上限会空转烧 Token；两模型互夸会「假通过」                  |

最少护栏：

| 护栏         | 作用                                        |
| ------------ | ------------------------------------------- |
| `max_rounds` | 硬停，到点输出当前最佳或 `failed`           |
| 通过标准     | 测试绿、Schema 合法、规则打分、业务状态已变 |
| 无改进检测   | 连续两轮 diff 为空 / 同分 → 退出            |

#### Reflection / Critic（Loop 的常见形态）

```text
Generator → Result → Critic → Pass → Output
                         └→ Fail → Revise → Generator
```

- **Generator**：产出候选（文案、补丁、SQL…）  
- **Critic**：相对**可检查标准**判 Pass/Fail，并给出可执行修订点  
- **Revise**：按 Critic 意见改，再进下一轮  

Critic 应尽量挂硬标准（单测、linter、Schema、政策规则）；若 Critic 也只是「另一个模型凭感觉」，容易两个模型互相恭维，Loop 失去意义。

**例：** Coder 改代码 → 跑测试（Critic 的硬门槛）→ 红则带着失败日志回 Coder；不要只用「Reviewer 模型说 LGTM」当完成。

### 10.4 怎么拼、怎么选（简表）

| 结构       | 先问一句                                          |
| ---------- | ------------------------------------------------- |
| Sequential | 没有上一步产出，下一步能不能开工？能 → 串行       |
| Parallel   | 各路是否互不等待？合并规则是否已写清？是 → 可并行 |
| Loop       | 有没有硬通过标准 + 最大轮次？有 → 才允许转        |

实际业务图往往是混合：先 Parallel 调研 → Sequential 成文 → Loop 审改；而不是三选一教条。

## 11. Tools：Function Calling、Skills、MCP

工具相关名词常被并列成「四种工具」，其实**不在同一层**。搞清分层，才知道该设计 Schema、该写流程说明，还是该上标准接入协议。

工具层回答的是：**能力怎么被提出、发现、接入与执行**。它不是 Reasoning / Workflow 本身，但 Agent 要「做事」离不开它。

### 11.1 分层总览

```text
用户目标
   │
   ▼
Agent Skill              ← 怎么做：流程、规范、禁忌、验收
   │
   ▼
Agent Loop / Workflow    ← 决策与编排
   │
   ▼
Function Calling         ← 模型提出：tool name + arguments
   │
   ▼
本地 Tool Registry / MCP ← 工具怎么被发现与接入
   │
   ▼
HTTP API / DB / 本地能力 ← 真正执行：副作用发生在这里
```

| 层级                 | 是什么                                                  | 解决什么                 | 不是什么                         |
| -------------------- | ------------------------------------------------------- | ------------------------ | -------------------------------- |
| **Skill**            | 可加载的流程/领域说明（产品侧常见 `SKILL.md` 一类约定） | 按正确方法做一类任务     | 不是开放协议，也不是可执行接口   |
| **Function Calling** | 模型与应用之间的调用约定（又称 Tool Use）               | 稳定产出可执行的调用意图 | 不是业务 API，也不负责真正执行   |
| **MCP / Registry**   | 工具发现与接入（标准协议或本地注册表）                  | 统一或集中地暴露可调能力 | 不是业务中台；MCP 常包装已有能力 |
| **HTTP API 等**      | 真实服务端能力                                          | 鉴权、事务、幂等、副作用 | 不是给模型「聊天」用的协议       |

### 11.2 Function Calling（Tool Use）

模型在生成普通文本之外，还能返回结构化调用请求，例如：

```json
{
  "name": "get_order",
  "arguments": { "orderId": "A1" }
}
```

应用侧校验并执行后，把结果作为 `tool`（或等价）消息写回上下文，进入下一轮 Loop。  
相对「请在回复里自己写一段 JSON」，厂商原生 Tool Calling 通常更稳，参数可用 JSON Schema 约束。

要点：

- **只表达意图**：不保证执行成功，也不自动带权限。  
- **决策与执行分离**：模型提议，运行时执行——权限、白名单、确认必须在执行层。  
- **工具面要可控**：工具过多时易选错/漏调/重复调，需要分组、路由或检索，而不是无限注册。  
- 供应商字段名、并行调用、流式 `tool_call` 细节不同，生产上常要一层内部模型适配。

### 11.3 Agent Skill

Skill 教的是**行为策略**：何时启用、步骤顺序、质量标准、输出格式、该用哪些工具、哪些事不能做。它改变的是「怎么做」，不是再暴露一个 HTTP 接口。

说明：Skill **不是**与 MCP 同级的开放互操作标准，而是不少产品里「可发现、可按需加载的任务说明书」约定（常见落地为目录 + `SKILL.md`）。机制上它仍是进上下文的指令与流程文本。

可记：

> Skill 是菜谱；Tool 是锅铲；API 是水电；Function Calling 是「现在用哪把铲子」。

要点：

- 适合沉淀可复用方法论（排查手册、评审清单、发布检查），按需加载，避免塞爆 System Prompt。  
- **本身通常不执行副作用**；真改数据仍走 Tool → API。  
- 写太长占窗口，写太虚无约束；且**不能替代**服务端鉴权（Prompt / Skill 里的「先确认再删」可被忽略或注入绕过）。  
- 和普通 Prompt 模板有重叠，但 Skill 更强调可分发、可发现、按任务触发。

### 11.4 MCP 与本地 Registry

**本地 Tool Registry：** 进程内注册 `name → 实现 + Schema`，单应用最常见、也最够用。  
**MCP（Model Context Protocol）：** 用 Client/Server 标准方式暴露 Tools / Resources 等；对 Agent 仍表现为「可发现、带 Schema、可调用」的工具，对服务端常常是对已有 API/本地能力的封装。

```text
直连：  Agent → 各厂商/内部 SDK（自管 Schema 与鉴权）
MCP：   Agent → MCP Client → MCP Servers → 外部系统
```

|      | 本地 Registry      | MCP                                       |
| ---- | ------------------ | ----------------------------------------- |
| 优点 | 简单、路径短、易控 | 发现与接入形态更统一，利多客户端复用      |
| 成本 | 每个应用自建一套   | 多一层运维与权限边界                      |
| 何时 | 单产品、工具少而稳 | 多 IDE/Agent 共用同一批能力，或插件化接入 |

MCP **不替代** Planning、状态机、Eval；对模型侧最终往往仍要通过 Function Calling（或等价机制）被选中。权限、租户、审计仍要自己做。

### 11.5 一条典型链路（串起来）

1. 用户：「订单 A1 支付成功但没发货，帮我查。」  
2. 加载 **Skill**（排查手册）：先订单 → 再支付 → 再履约 → 结论须带证据。  
3. 模型经 **Function Calling** 提出 `get_order` / `get_payment`。  
4. Runtime 从 **Registry 或 MCP** 解析 Schema、校验参数并执行。  
5. 工具内部打公司 **HTTP API**，副作用与鉴权在这里发生。  
6. 观察结果回灌 Loop；若要退款/补发，走高风险确认，而不是模型直接「说完就算办成」。

### 11.6 选型与工程原则

1. **先有可治理的 API/能力，再包成给模型的 Tool**（Tool 应比原始 API 更窄、更任务化）。  
2. **单应用：Function Calling + 本地 Registry 通常够用；跨客户端复用再上 MCP。**  
3. **重复流程与验收标准 → Skill；一次性口头指令不必硬做成 Skill。**  
4. **权限 / 幂等 / 审计放在执行层**，不要只写在 Skill 或 Tool 描述里。  
5. 工具要有 **Schema、超时、错误码**；副作用默认确认或二次校验；结果入窗前**截断/结构化**。

## 12. 事件驱动（平台级可选）

大规模、异步、长任务平台可能演进为：

```text
Agent 发布事件 → Queue / Bus → 订阅方 Agent 消费
```

这与微服务事件驱动同构：解耦、可扩、可重放；也带来最终一致性、重复消费、调试变难。

**适合：** Agent Platform、后台自动化、长任务异步化。  
**不适合：** 作为第一个业务 Agent 的默认架构——复杂度通常早于收益。

## 13. 怎么选型

| 形态                     | 更适合                 | 先问清楚                    |
| ------------------------ | ---------------------- | --------------------------- |
| Single Agent + Tools     | 边界清晰、步骤少       | 有无 max_steps / 权限？     |
| Graph / Workflow         | 业务流程、要恢复与审计 | 状态字段与节点契约定了吗？  |
| Supervisor + Specialists | 多领域、要分工         | 子 Agent 输出 Schema 有吗？ |
| Orchestrator + Workers   | 可并行调研/分片        | 合并与冲突策略有吗？        |
| Handoff                  | 意图路由、多角色       | 防环与上限有吗？            |
| Reflection / Critic      | 要抬质量               | Critic 的硬标准是什么？     |
| Event-Driven             | 平台级异步             | 是否已有队列与幂等基建？    |
| 「自由多 Agent 聊天」    | 实验                   | 生产默认不选                |

经验顺序（多数业务）：

```text
先 Single Agent + 硬护栏
  → 流程变复杂再上 Graph
  → 领域明显再拆 Specialist
  → 可并行再上 Workers
  → 平台化再考虑事件驱动
```

## 14. Agent Loop：工作流程抽象

架构回答「用什么拓扑」；工作流程回答「每一跳实际在干什么」。完整循环可抽象为：

```text
Goal
  ↓
Task Understanding          ← 用户说了什么 vs 要完成什么
  ↓
Context / Memory Retrieval  ← 证据、笔记、任务状态入窗
  ↓
Planning（可选）            ← 简单任务可跳过
  ↓
Tool Selection
  ↓
Action（Tool Call）
  ↓
Observation
  ↓
Evaluation（相对 Success Criteria）
  ↓
  ├─ 达标 → Output / 副作用确认完成
  └─ 未达标 → Replan / 换工具 / 问用户 / 升级人工 → 再入环
```

对照前端：这像一次带副作用的请求状态机（pending → calling → observing → deciding），不是「渲染一段 Markdown 就结束」。

区分两种「状态」，避免混用：

|                  | 管什么                           | 丢了会怎样           |
| ---------------- | -------------------------------- | -------------------- |
| **Conversation** | 多轮对话消息（给模型看的历史）   | 答非所问、重复追问   |
| **Task State**   | 任务进度、计划、确认态、业务字段 | 无法断点续跑、假完成 |

建议把下列字段写进 **Task State**（可持久化），而不是只活在模型散文里：

| 字段               | 作用                                                           |
| ------------------ | -------------------------------------------------------------- |
| `goal`             | 本任务真正要完成的事                                           |
| `constraints`      | 硬约束（权限、禁止项、时限）                                   |
| `success_criteria` | 可检查的完成条件                                               |
| `plan` / `step`    | 当前计划与步号（可空）                                         |
| `last_observation` | 最近工具/用户反馈摘要                                          |
| `status`           | `running \| waiting_human \| succeeded \| failed \| cancelled` |

## 15. 流程上要钉死的七个问题

### 15.1 目标是否明确

区分：

- **用户原话**（utterance）  
- **任务目标**（goal）  
- **成功标准**（success criteria）  

开放任务务必显式维护三者。模糊目标会在循环里「看起来很忙、从未完成」。

### 15.2 什么时候规划

| 任务类型             | 建议                                             |
| -------------------- | ------------------------------------------------ |
| 单步查询、单工具可解 | **跳过**复杂 Planning，直接选工具                |
| 多步、多工具、有依赖 | 先短计划（3～7 步内），边做边改                  |
| 强业务流程           | 计划下沉到 **Workflow 节点**，模型只填节点内决策 |

过度 Agent 化（凡事先写长计划）只会抬延迟与 Token，且计划本身易幻觉。

### 15.3 什么时候调用工具

Tool Calling 的完整决策链：

```text
要不要调 → 调哪个 → 参数对不对 → 结果可信吗 → 失败怎么走
```

落地检查：

- **要不要调：** 窗口里是否已有足够证据？纯生成能否验收？  
- **调哪个：** Schema / 描述是否让模型能区分近似工具？  
- **参数：** 类型与必填校验在执行前做（应用层），不要等下游 400。  
- **可信：** 结果是否过期、是否与 `facts` 冲突、是否需二次查询。  
- **失败：** 超时 / 5xx / 业务错误码分别：重试、换工具、问用户、标记 failed。

「模型发起了 tool_calls」≠「这一步做对了」。

### 15.4 如何处理不确定性

不确定时不要假装确定。分支应写进编排，而不是指望模型「自觉」：

| 信号             | 常见动作                 |
| ---------------- | ------------------------ |
| 缺关键字段       | 问用户 / 调查询工具      |
| 工具结果矛盾     | 换源交叉验证或升级       |
| 同一步重复失败   | 换策略或终止，禁止盲重试 |
| 超出权限或高风险 | 人工确认                 |
| 目标本身不可达   | 明确失败原因，不要空转   |

### 15.5 如何控制循环

ReAct 形态天然会：

```text
Think → Act → Observe → Think → Act → …
```

没有护栏就会烧预算。最少配置：

| 护栏                    | 说明                                      |
| ----------------------- | ----------------------------------------- |
| `max_steps`             | 硬上限，到点必须收束或失败                |
| `max_cost` / Token 预算 | 成本熔断                                  |
| Timeout                 | 单工具与整任务两级                        |
| 重复行为检测            | 相同工具+相同参数连续 N 次 → 终止或换策略 |
| 失败终止条件            | 不可重试错误直接 `failed`，不回环         |

### 15.6 什么时候需要人工确认

按风险分级（示例，按业务改）：

| 操作类型               | 默认策略               |
| ---------------------- | ---------------------- |
| 只读查询               | 自动                   |
| 低风险、可回滚的修改   | 可自动（建议审计日志） |
| 发邮件 / 提交外部表单  | 视场景确认或草稿待发   |
| 转账 / 删数据 / 改权限 | **强制确认**           |

成熟 Agent 的标志不是「全自动」，而是**知道何时不能自动**。确认态应进入 `waiting_human`，恢复时带上人的决策写入 State。

### 15.7 如何判断完成

不要把「模型生成了一段话」当成完成。用 **Success Criteria** 对照副作用/系统状态。

例：用户说「帮我安排会议」

| 中间产物                                   | 是否完成 |
| ------------------------------------------ | -------- |
| 生成几个时间建议                           | 否       |
| 查到双方空闲时段                           | 否       |
| 日历事件已创建且邀请已发出（工具成功回执） | **是**   |

完成判定尽量用：工具回执、DB 状态、规则校验——而不是模型自称「已完成」。

## 16. 生产优先级（五条不等式）

在架构选型与流程设计之上，落地时建议按此排序（不是否定右侧，而是**先补左侧短板**）：

### 16.1 Workflow > Prompt

先把任务流程、节点契约、失败分支设计清楚，再抠 System Prompt。稳定 Workflow 通常比堆砌复杂提示更管用。

### 16.2 State > Memory

先解决「任务执行到哪一步」（Task State），再谈长期记忆与个性化。没有 State，记忆只是另一堆噪声上下文。

### 16.3 Tool Reliability > Model Intelligence

Agent = 模型 + 软件系统。API/DB/浏览器不稳、无幂等、无超时，再强模型也救不了。

### 16.4 Observability > Autonomy

越自主越要 Trace：为何调此工具、入参出参、下一步依据、错误落点、Token/费用。否则生产无法排障，也无法做 Eval。

### 16.5 Evaluation > Demo 观感

固定任务集持续测，例如：

- 任务成功率、工具选择/参数正确率  
- 幻觉或「假完成」率  
- 平均步数、延迟、Token 成本  
- 人工接管率  

「Demo 看起来聪明」不能替代回归。

外围最小闭环（与上表配套）：

```text
┌─────────────────────────────────────┐
│ Guardrails / Permissions / 鉴权     │
│ Timeout / Retry / 幂等              │
│ Tracing（每跳决策、工具、Token）     │
│ Eval（固定集回归）                   │
│ Cost / Token 预算与熔断             │
└─────────────────────────────────────┘
```

| 工程目标       | 落地含义                                     |
| -------------- | -------------------------------------------- |
| 任务能稳定完成 | Success Criteria + 终止条件清晰              |
| 失败后能恢复   | Task State 持久化；可从节点 / 确认态重跑     |
| 出问题能解释   | Trace：prompt 版本、工具 I/O、分支原因、成本 |

Go 侧习惯对照：编排像带状态的状态机服务；工具调用像带超时与 `context.Context` 的出站 RPC；权限像 middleware；Trace/Cost 像统一拦截器——**模型调用只是其中一种出站依赖**。

## 17. 核心认识

1. **传统编程保正确，Workflow 控路径，Agent 做开放决策**；生产是组合，不是三选一。  
2. 核心范式（ReAct / Plan-and-Execute / Reflection / Multi-Agent 等）是控制模式；默认用 **Agentic Workflow** 包住它们。A2A 是互通层，不是又一种推理范式。  
3. Agent 架构的重点不是「堆更多 Agent」，而是**在可控流程里划出真正需要智能的判断点**。  
4. 生产默认优先 **Stateful Workflow / Graph**；Multi-Agent 是手段，不是目标；跨运行时协作才考虑 A2A。  
5. 工作流程要把 **Goal / Criteria / 循环护栏 / 人工边界** 写进 Task State；Conversation 历史不能替代任务进度。  
6. 工具相关要分层：Skill 管怎么做（产品约定，非开放协议），Function Calling 提调用，Registry/MCP 管接入，API 管执行与权限。  
7. 优先级：**Workflow > Prompt，State > Memory，Tool 可靠 > 模型更强，可观测 > 更自主，Eval > Demo**。  
8. 工程三目标：**做完、可恢复、可解释**（含成本可解释）。
