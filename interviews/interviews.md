# 面试相关内容

## SSE、WebSocket 和 HTTP chunked 这三种流式协议怎么选

先说结论：

- **服务端单向、事件化推送**，例如大模型逐字输出、通知、任务进度，优先选 **SSE**。
- **客户端和服务端都要高频、低延迟地发送消息**，例如即时聊天、协同编辑、在线游戏，选 **WebSocket**。
- **只需要让普通 HTTP 响应边生成边返回，且愿意自行定义数据边界和重连逻辑**，可以使用 **HTTP 流式响应**；在 HTTP/1.1 中常由 `Transfer-Encoding: chunked` 承载。

需要特别说明：三者并不完全处于同一层级。SSE 是一种基于 HTTP 的事件流格式，WebSocket 是独立的全双工通信协议，而 chunked 是 **HTTP/1.1 的传输编码方式**，用于表示响应体长度未知，并不是完整的业务层流式协议。SSE 在 HTTP/1.1 下也可能由 chunked 承载。

### 核心区别

| 维度 | SSE | WebSocket | HTTP chunked / 普通 HTTP 流 |
| --- | --- | --- | --- |
| 通信方向 | 服务端到客户端单向推送；客户端另发 HTTP 请求 | 全双工，双方可随时发送 | 通常是服务端到客户端持续返回响应体 |
| 底层连接 | HTTP 长连接 | HTTP 握手后升级为 WebSocket；HTTP/2 下也可使用扩展 CONNECT | HTTP/1.1 响应使用 chunked 编码；HTTP/2、HTTP/3 使用各自的数据帧 |
| 数据格式 | `text/event-stream`，有标准事件格式 | 文本帧或二进制帧 | 无统一业务格式，需自行设计 NDJSON、分隔符或长度前缀 |
| 浏览器支持 | 原生 `EventSource`，也可使用 `fetch` 读取流 | 原生 `WebSocket` | 使用 `fetch` + `ReadableStream` 读取 |
| 自动重连 | `EventSource` 原生支持，可配合 `id`、`retry` 和 `Last-Event-ID` | 没有，需要应用层实现 | 没有，需要应用层实现 |
| 二进制 | 不直接支持，只传 UTF-8 文本；二进制需编码，开销较大 | 原生支持 | 可以传二进制 |
| 协议开销 | 较低，事件有少量文本字段开销 | 握手后帧开销低，适合高频消息 | 最低程度取决于自定义格式 |
| 代理与基础设施兼容性 | 通常较好，但要关闭代理缓冲并设置足够长的超时 | 需要代理、网关和负载均衡器支持连接升级 | 与普通 HTTP 最接近，但仍可能被代理缓冲 |
| 典型场景 | LLM 输出、通知、日志、进度、行情展示 | 聊天、协同编辑、游戏、实时音视频信令 | 文件生成、媒体分段、NDJSON、内部服务流式接口 |

### SSE

SSE（Server-Sent Events）让服务端通过一个持续打开的 HTTP 响应向客户端发送事件。响应的 `Content-Type` 为 `text/event-stream`，事件之间以空行分隔：

```text
id: 42
event: message
data: {"content":"hello"}

```

#### 优势与特点

- 基于 HTTP，通常比 WebSocket 更容易接入现有鉴权、日志、网关和负载均衡体系。
- 具有标准的 `data`、`event`、`id`、`retry` 字段，客户端不必重新设计事件边界。
- 浏览器 `EventSource` 支持断线重连；服务端可根据 `Last-Event-ID` 补发遗漏事件。
- 非常适合“请求一次，服务端持续返回多个增量事件”的模型 API。

#### 边界与注意事项

- 原生 `EventSource` 只能发起 GET 请求，不方便提交复杂请求体，也不能自由设置 `Authorization` 等自定义请求头。常见做法是使用 Cookie、先 POST 创建任务再用 SSE 订阅，或改用 `fetch` 手动解析 SSE。
- SSE 是单向通道。客户端需要发送数据时，仍要使用普通 HTTP 请求；如果双方都持续高频通信，WebSocket 更合适。
- 数据必须是 UTF-8 文本，不适合直接传输大量二进制数据。
- HTTP/1.1 浏览器对同一域名的并发连接数通常有限；多标签页各开 SSE 连接时可能达到上限。HTTP/2 多路复用能缓解这个问题。
- 代理可能缓存数据，导致服务端已经写出但客户端迟迟收不到。通常需要关闭缓冲，例如设置 `X-Accel-Buffering: no`，并定期发送心跳注释，避免空闲连接被网关关闭。
- 自动重连不等于不会重复或丢失事件。需要结合事件 ID、幂等处理和服务端保留策略保证恢复语义。

#### 适用场景

- 大模型 Token 或增量消息输出
- 构建、导出、异步任务的进度更新
- 系统通知、监控指标、日志尾随
- 只读行情或状态变化推送

### WebSocket

WebSocket 建立连接后，客户端和服务端都可以主动发送文本或二进制帧，不需要遵循 HTTP 的一问一答模式。

#### 优势与特点

- 真正的全双工通信，适合双方持续、高频、低延迟交互。
- 原生支持消息帧和二进制，不需要依靠换行符判断消息边界。
- 建连后每条消息的协议开销较小，适合大量小消息。
- 可以在同一连接上自定义订阅、发布、确认、心跳等应用层协议。

#### 边界与注意事项

- 浏览器原生 WebSocket API 不提供自动重连、消息确认、断点续传和请求响应关联，需要自行实现，或使用更高层协议。
- 长连接会增加服务端连接管理成本，需要处理心跳、连接清理、限流、背压以及服务端扩缩容。
- 多实例部署时，如果消息与具体连接绑定，通常需要粘性会话，或通过 Redis、Kafka 等消息系统把事件路由到持有连接的实例。
- 某些企业代理、防火墙、Serverless 平台或负载均衡器对 WebSocket 支持有限，还需正确配置连接升级和空闲超时。
- WebSocket 只保证帧在单条连接内有序送达；业务上的“恰好一次”、离线消息和重连补偿仍需应用层实现。
- 对低频、单向更新而言，WebSocket 的协议和运维复杂度往往没有必要。

#### 适用场景

- 双向即时聊天和客服系统
- 多人协同编辑、白板和光标同步
- 在线游戏状态同步
- 实时控制、设备交互
- WebRTC 等实时系统的信令通道

### HTTP chunked / 普通 HTTP 流式响应

HTTP/1.1 的 chunked transfer encoding 会把响应体拆成若干块发送，因此服务端无需提前声明 `Content-Length`。但这里的“块”只是传输层边界，不应直接视为一条业务消息：

- 一条 JSON 消息可能被拆到多个网络块中。
- 多条消息也可能合并到一次客户端读取中。
- UTF-8 字符甚至可能横跨两次读取。

因此客户端必须使用增量解码器，并根据明确的应用层格式重新组装消息。常见格式有：

- **NDJSON**：每行一个 JSON，简单且便于调试。
- **长度前缀**：先写消息长度，再写消息内容，适合二进制。
- **自定义分隔符**：实现简单，但必须处理转义和数据中包含分隔符的情况。

#### 优势与特点

- 保持普通 HTTP 请求—响应语义，适合一次请求对应一个持续产生的响应。
- 可使用 POST、请求体、自定义请求头和现有 HTTP 鉴权机制。
- 对二进制和自定义数据格式限制少。
- 服务端能边计算边发送，减少首字节时间和内存占用，例如边生成边下载大型文件。

#### 边界与注意事项

- chunked 仅存在于 HTTP/1.1；HTTP/2 和 HTTP/3 不使用 `Transfer-Encoding: chunked`，但仍可通过 DATA 帧实现流式响应。因此更准确的说法是“HTTP 流式响应”。
- 传输块边界不稳定，不能把一次 `read()` 当成一条完整消息。
- 没有 SSE 那样统一的事件类型、事件 ID 和自动重连语义，协议设计、错误表示和断点恢复都由应用负责。
- 浏览器或中间代理可能缓冲较小的数据块。除关闭代理缓冲外，还应避免压缩器为了提高压缩率而积攒数据。
- HTTP 状态码和响应头在流开始后就无法修改。若中途发生业务错误，只能在流内定义错误消息，或直接终止连接。
- 客户端读取速度跟不上时必须处理背压，否则服务端可能持续占用内存。

#### 适用场景

- 动态生成并下载大型文件
- 内部服务之间传输 NDJSON 或二进制流
- 音视频或数据处理管道的分段输出
- 需要 POST 和自定义请求头，但又不需要双向长连接的流式接口

### 选型方法

可以按下面的顺序判断：

1. **是否需要双方随时主动发送数据？** 是则选 WebSocket。
2. **是否主要由服务端持续推送文本事件？** 是则优先 SSE。
3. **是否需要 POST、二进制或完全自定义的数据格式？** 是则考虑普通 HTTP 流式响应。
4. **是否需要自动重连和断点续传？** SSE 提供基础机制；其他方案需要自行实现，但无论哪种方案，可靠性语义都要由业务层补足。
5. **基础设施是否支持长连接？** 检查网关缓冲、空闲超时、连接数、HTTP 版本、扩缩容和负载均衡策略。

大模型聊天通常使用 **POST + SSE 语义的流式响应**：客户端通过 POST 提交上下文，服务端以 `text/event-stream` 持续返回增量事件。浏览器端因为原生 `EventSource` 不支持 POST，常使用 `fetch` 读取 `ReadableStream` 并解析 SSE。只有当产品还需要同一连接承载用户实时输入、语音数据、协作状态等双向消息时，才有必要升级为 WebSocket。

## JSON Mode、JSON Schema、Structured Outputs 有什么区别

先用一句话区分：

- **JSON Mode：** 保证输出是合法 JSON，但不保证字段对不对。
- **JSON Schema：** 描述“合法结构长什么样”，本身不是模型能力，而是规则说明书。
- **Structured Outputs：** 让模型按 Schema 生成，尽量保证结构真的符合你的要求。

可以把它想成填表：

| 能力 | 通俗理解 | 保证到什么程度 |
| --- | --- | --- |
| 普通 Prompt 要求“请返回 JSON” | 口头提醒对方填表 | 最弱，容易多解释、漏字段、格式坏掉 |
| JSON Mode | 要求“必须交一张合法表单” | 保证是 JSON，不保证字段齐全、类型正确 |
| JSON Schema | 表单模板：有哪些字段、什么类型、哪些必填 | 只是约束定义，需要配合校验或结构化输出能力 |
| Structured Outputs | 系统按模板强制填写 | 强约束结构，业务上通常可直接解析使用 |

### JSON Mode

JSON Mode 的目标很单一：**输出必须是可解析的 JSON**。

面试里可以这样说：

> JSON Mode 解决的是“能不能 `JSON.parse`”，不是“字段是否符合业务”。

例如你希望返回：

```json
{"name":"张三","age":28}
```

开启 JSON Mode 后，模型可能返回：

```json
{"user":"张三","years":28,"note":"ok"}
```

这也是合法 JSON，但业务字段已经对不上了。

#### 优势与特点

- 比纯 Prompt 约束更稳，减少 markdown 代码块、前后多余解释。
- 实现成本低，适合先把“能解析”这件事做稳。
- 适合对结构要求不严、后续还会自己校验和纠错的场景。

#### 边界与注意事项

- 不保证字段名、类型、必填项、枚举值正确。
- 仍可能返回空对象、多余字段或业务语义错误。
- 不同供应商开关名称和支持程度不完全一致。
- 流式场景下仍要等完整内容再 `JSON.parse`，不能对半截字符串直接解析。

#### 适用场景

- 只想稳定拿到 JSON，后续自己做 Schema 校验
- 结构较松、允许一定容错和重试修复
- 快速接入，暂未接入更强的结构化输出能力

### JSON Schema

JSON Schema 是**结构描述语言**，用来定义对象应该长什么样。它不是大模型专属概念，后端接口、表单校验、OpenAPI 里都很常见。

一个简化例子：

```json
{
  "type": "object",
  "properties": {
    "name": { "type": "string" },
    "age": { "type": "integer", "minimum": 0 },
    "role": { "type": "string", "enum": ["admin", "user"] }
  },
  "required": ["name", "age", "role"],
  "additionalProperties": false
}
```

这张“说明书”表达的是：

- 必须是对象
- 必须有 `name`、`age`、`role`
- `age` 必须是非负整数
- `role` 只能是 `admin` 或 `user`
- 不允许额外字段

#### 优势与特点

- 把口头 Prompt 变成机器可校验的契约。
- 前后端、模型层、校验层可以共用同一份定义。
- 既能指导模型生成，也能做生成后校验。
- 也是 Tool Calling / Function Calling 参数定义的常见载体。

#### 边界与注意事项

- Schema 本身不会自动让模型变听话；没有 Structured Outputs 或后置校验时，它只是“期望”。
- 不同供应商支持的 Schema 子集不同，复杂特性如 `$ref`、`oneOf`、`format` 可能不完全支持。
- Schema 过严会导致拒答或生成失败；过松又拦不住脏数据。
- 业务规则不等于 Schema。例如“年龄必须小于入职年限”这类跨字段逻辑，通常还要额外校验。

#### 适用场景

- 定义工具参数
- 定义接口响应结构
- 作为 Structured Outputs 的输入约束
- 生成后做本地 Schema 校验

### Structured Outputs

Structured Outputs 可以理解为：**把 JSON Schema 真正接到模型输出链路里**，让模型按指定结构生成，而不是只“尽量返回 JSON”。

面试金句：

> JSON Mode 管语法，Structured Outputs 管结构，JSON Schema 是两者之间的契约。

#### 优势与特点

- 字段、类型、必填、枚举等约束更强，生产系统更敢直接落库或调下游接口。
- 减少“先解析，再修 JSON，再重试”的胶水代码。
- 比纯 Prompt 更稳定，比只开 JSON Mode 更贴近业务。
- 和 Tool Calling 很像：Tool Calling 产出的是“调用某个工具的参数”，Structured Outputs 产出的是“最终业务对象”。

#### 边界与注意事项

- 强约束结构，不代表内容正确。字段合法，值仍可能是幻觉。
- 供应商能力差异大，有的叫 Structured Outputs，有的通过 `response_format`、JSON Schema、Tool 强制调用实现。
- 复杂 Schema、嵌套过深、流式结构化，都可能有兼容限制。
- 流式时不要边收边 `JSON.parse` 完整对象；应累积到结束事件，或使用官方/SDK 累积器，再做 Schema 校验。
- 解析失败可以做 1～2 次格式修复重试，但不要无限重试。

#### 适用场景

- 提取订单、用户画像、工单字段等结构化结果
- Agent 决策对象、路由结果、评分卡
- 需要直接写入数据库或调用强类型接口
- 多供应商网关中需要统一输出契约

### 和 Function Calling / Tool Use 的关系

三者常被一起问，可以这样区分：

| 方式 | 主要目的 | 输出像什么 |
| --- | --- | --- |
| JSON Mode | 让回答是合法 JSON | `{"a":1}` |
| Structured Outputs | 让回答符合业务 Schema | `{"orderId":"A1","status":"paid"}` |
| Function Calling / Tool Use | 让模型提出工具调用 | `search_order({orderId:"A1"})` |

经验法则：

1. 只要最终结果，不调用外部工具：优先 Structured Outputs。
2. 需要查库、搜网页、算价格、发请求：用 Tool Calling，参数仍用 JSON Schema 定义。
3. 供应商不支持 Structured Outputs：JSON Mode + 本地 JSON Schema 校验 + 有限次修复重试。
4. 只在 Prompt 里写“请返回 JSON”：可以做 Demo，不适合作为生产主方案。

### 面试时怎么答

推荐回答结构：

1. **先分层：** JSON Mode 管语法正确，JSON Schema 管结构定义，Structured Outputs 管按结构生成。
2. **再举例：** “能 parse 成功”不等于“有 `name/age` 且类型正确”。
3. **落生产：** 生产链路通常是 Schema 定义 → Structured Outputs 或 JSON Mode 生成 → 本地校验 → 失败有限重试 → 观测错误率。
4. **补一句边界：** 结构化约束解决的是格式稳定性，不解决事实正确性和业务正确性。

## Function Calling、MCP Tool、HTTP API、Agent Skill 应该怎么分层

先说结论：

- **HTTP API：** 真正做事的能力层，负责鉴权、限流、幂等、事务和副作用。
- **Function Calling：** 模型表达“我要调哪个工具、参数是什么”的协议层。
- **MCP Tool：** 把外部能力以统一协议暴露给 AI 客户端的适配层。
- **Agent Skill：** 教 Agent“什么时候、按什么流程、用什么约束去做事”的知识/流程层。

它们不在同一层，也不互相替代。面试里最怕把四者说成四种并列工具。

### 分层总览

```text
用户目标
   │
   ▼
Agent Skill          ← 怎么做：流程、规范、选型、禁忌
   │
   ▼
Agent Loop
   │  决策与编排
   ▼
Function Calling     ← 模型怎么提出调用：tool name + arguments
   │
   ▼
MCP Tool / 本地 Tool Registry  ← 工具怎么被发现和接入
   │
   ▼
HTTP API / DB / 文件系统等     ← 真正执行：副作用发生在这里
```

| 层级 | 它是什么 | 解决什么问题 | 不是什么 |
| --- | --- | --- | --- |
| Agent Skill | 可加载的流程说明和领域知识 | 让 Agent 按正确方法完成一类任务 | 不是可执行接口，也不直接产生副作用 |
| Function Calling | 模型与应用之间的工具调用约定 | 让模型稳定产出可执行的调用意图 | 不是业务 API，也不负责真正执行 |
| MCP Tool | 工具发现与调用的标准协议封装 | 让不同客户端用同一方式接入工具 | 不是业务本身，通常包装已有能力 |
| HTTP API | 稳定的服务端业务接口 | 提供可治理的真实能力 | 不是给模型直接“聊天”用的协议 |

### HTTP API：能力底座

HTTP API 是系统真正对外提供能力的地方。查订单、扣库存、发邮件、创建工单，最终都落在这里。

#### 优势与特点

- 契约稳定，适合长期演进、版本管理和多端复用。
- 鉴权、限流、审计、幂等、超时、重试都可以按成熟后端规范落地。
- 人类客户端、服务间调用、Agent 工具背后，都可以共用同一套 API。
- 副作用边界清晰：谁改了数据、如何回滚、如何观测，都在这一层处理。

#### 边界与注意事项

- 直接把几百个内部 API 原样塞给模型，工具面会爆炸，模型也难选对。
- API 为程序员设计，字段多、错误码细；给 Agent 用时通常需要再包一层更窄的工具接口。
- API 正确不等于 Agent 会正确使用；还需要调用策略、确认流程和失败处理。

#### 适用场景

- 所有需要持久化、计费、权限控制的真实业务动作
- 多系统集成与服务间调用
- Agent 工具背后的真实执行实现

### Function Calling：模型提出调用的方式

Function Calling / Tool Use 让模型在生成文本之外，还能返回结构化的工具调用请求，例如：

```json
{
  "name": "get_order",
  "arguments": { "orderId": "A1" }
}
```

应用收到后自己执行工具，再把结果塞回对话，进入下一轮 Agent Loop。

#### 优势与特点

- 比“请在回复里写 JSON 告诉我要调什么”更稳定。
- 参数通常用 JSON Schema 约束，便于校验。
- 把“决策调用”和“真正执行”拆开：模型提议，应用执行。
- 是 Agent 能操作外部世界的关键机制。

#### 边界与注意事项

- Function Calling 只表达意图，不保证执行成功，也不自动具备权限。
- 工具太多时，模型容易选错、漏调或重复调用，需要检索、分组或路由。
- 不同供应商的字段名、并行调用、流式 tool_call 细节不同，生产上要做兼容层。
- 危险操作不能只靠模型自觉，必须有服务端鉴权、白名单和人工确认。

#### 适用场景

- 对话中动态决定查库、搜索、计算、创建单据
- Agent Loop 的标准工具调用链路
- 需要把工具参数从自然语言稳定抽出时

### MCP Tool：统一接入外部工具

MCP（Model Context Protocol）把工具、资源、提示等能力，通过标准 Client/Server 协议暴露给 AI 应用。对 Agent 来说，MCP Tool 往往表现为“可发现、带 Schema、可调用”的工具；对服务端来说，它常常是对 HTTP API、数据库或本地能力的一层标准化封装。

#### 优势与特点

- 工具发现和调用方式标准化，减少每个模型厂商各写一套插件协议。
- 适合把 IDE、浏览器、数据库、内部系统能力接到不同 Agent 客户端。
- 传输可选 stdio、HTTP 等，本地工具和远程工具都能接入。
- 把“能力提供方”和“Agent 运行时”解耦：Server 负责能力，Client 负责编排。

#### 边界与注意事项

- MCP 是接入协议，不是业务中台。没有稳定 HTTP API / 领域服务时，只上 MCP 扛不住复杂治理。
- 工具权限、租户隔离、审计日志仍要自己做，协议不会自动给你生产级安全。
- 不是所有场景都需要 MCP；单应用内几个本地函数，用本地 Tool Registry 往往更简单。
- MCP Tool 对模型侧最终仍要通过 Function Calling 或等价机制被选中和调用。

#### 适用场景

- 多个 Agent / IDE / 客户端要复用同一批工具
- 把外部系统能力以标准方式暴露给 AI
- 本地开发工具链、企业知识库、内部平台插件化接入

### Agent Skill：教 Agent 怎么做

Agent Skill 通常是一份可被加载的说明，例如 `SKILL.md`：描述何时启用、步骤顺序、质量标准、输出格式、该用哪些工具、哪些事不能做。它改变的是 Agent 的行为策略，而不是直接提供一个新的 HTTP 接口。

可以把它理解成：

> Skill 是菜谱，Tool 是锅铲和炉灶，HTTP API 是厨房供水供电，Function Calling 是厨师决定“现在用哪把铲子”。

#### 优势与特点

- 把团队经验沉淀成可复用流程，而不是每次靠口头 Prompt 现场发挥。
- 适合编码规范、评审清单、发布流程、排查手册这类“有固定方法论”的任务。
- 可以按场景按需加载，避免把所有规则一股脑塞进 System Prompt。
- 能指导如何组合多个工具，而不只是暴露单个工具。

#### 边界与注意事项

- Skill 本身通常不执行副作用；真正做事仍要通过 Tool / API。
- 写得太长会挤占上下文，写得太虚又无法约束行为。
- Skill 不能替代权限系统。即使 Skill 写了“先确认再删除”，服务端仍要强制校验。
- 和 Prompt 模板有重叠，但 Skill 更强调可分发、可发现、可在特定任务触发。

#### 适用场景

- 规范化工作流：PR 审查、提交信息、发布检查、事故排查
- 领域打法：SEO 审计、安全复盘、数据分析步骤
- 需要稳定教 Agent“先做什么、后做什么、如何验收”

### 四者如何协作

一个典型调用链：

1. 用户说：“帮我排查为什么订单 A1 支付成功但没发货。”
2. Agent 命中或加载 **Skill**：客服排查手册，要求先查订单，再查支付，再查履约，最后给出结论和证据。
3. 模型通过 **Function Calling** 提出调用 `get_order`、`get_payment`。
4. 运行时发现这些工具来自 **MCP Server** 或本地注册表，完成参数校验并执行。
5. 工具内部请求公司的 **HTTP API**，返回订单和支付数据。
6. Agent 按 Skill 约定汇总结果；若要执行退款或补发，再走高风险确认和鉴权。

### 选型与分层原则

1. **先有稳定 HTTP API，再考虑是否包装成 Tool。**  
   没有可治理的能力底座，Agent 只会不稳定地撞系统。

2. **给模型的 Tool 要比 HTTP API 更窄、更任务化。**  
   例如不要直接暴露 `PATCH /orders/{id}` 的全部字段，而提供 `mark_order_shipped(orderId)`。

3. **单产品内部工具，本地 Function Calling + Tool Registry 通常够用；跨客户端复用再上 MCP。**  
   MCP 的价值在标准接入和生态复用，不在“看起来更 AI”。

4. **重复出现的流程、规范、验收标准，沉淀为 Skill；单次临时指令不要硬做成 Skill。**

5. **权限、幂等、审计放在 API / 执行层，不要只写在 Skill 或 Tool 描述里。**  
   模型可能忽略说明，攻击者也可以通过 Prompt Injection 诱导调工具。

6. **按变更频率分层维护：**  
   - API：最稳定，强兼容  
   - Tool Schema：相对稳定，面向任务  
   - Skill：迭代最快，跟随方法论和业务经验

### 面试时怎么答

推荐回答结构：

1. **先纠偏：** 这四者不是并列四种工具，而是知识层、协议层、适配层、能力层。
2. **再画链路：** Skill 指导 → Function Calling 决策 → MCP/本地 Tool 接入 → HTTP API 执行。
3. **给边界：** Skill 不能代替鉴权；Function Calling 不能代替业务 API；MCP 不能代替领域服务。
4. **落选型：** 内部小工具本地注册，跨端复用上 MCP，稳定副作用进 HTTP API，复杂流程沉淀为 Skill。
